## 二、重叠面量化

| 维度 | 实查 |
|---|---|
| 生成核心 | **单一实现**：两者全部经 `src/paper_writer/paper_engine.py`（class PaperEngine :72）——无引擎逻辑重复，重复的是**输入语义与 UI 状态** |
| PaperEngine 函数面 | A 用实例方法 2 个（generate_questions :406 / generate_full_paper :455）；B 用模块级函数 5-6 个（paper_quick/reviewer_questions/revised_stream/paper_aware_qa/defense_qa/motivation_qa）——**函数集几乎不相交** |
| 独立逻辑行数 | A 的 678 行中，引擎调用点仅 3 处（:41/:406/:455），其余约 600 行为主题/方法/文献表单与预览 UI——**「可省 ~600 行」的口径即此**（KNOWN_ISSUES :58） |
| 信息重填成本 | A 需手填 ≥8 个字段（研究问题/假设/参与者/程序/理论/局限/实践/未来，:133-234）；B 从向导第 5 步产物直接取数，**A 的重填成本 = 用户在 B 已有数据时仍需逐字段重录** |
| 互补面（重叠的反例） | A 独有：文献搜索 tab（:302-404）、「无分析数据也可从零起稿」的起点；B 独有：反问式审阅、答辩 QA、分析产物联动 |

**判定**：重叠是「语义级」而非「代码级」——两条入口服务于同一段写作生命周期的不同起点（A=白纸起点，B=有数据起点），真正冗余的是 A 的方法/主题表单与 B 第 7 步的信息重复维护。

## 三、三方案设计稿（结构草案级）

### 方案 A：合并（A 入口并入向导第 7 步）
- 边界：删除 `src/ui/paper_writing_ui.py`；`app.py:2593-2596` 挂载点移除；把 A 独有的「文献搜索」抽为向导第 7 步的一个子面板（数据流：文献选择结果并入 generate_paper_quick 的 req）。
- 输入桥接：向导新增「白纸模式」开关——无第 5 步产物时，第 7 步就地渲染 A 的主题/方法最小表单（研究问题+假设+方法描述 3 个字段，非全 8 个），其余沿用分析产物。
- 规模：删 ~600 行、新增 ~150 行（白纸表单+文献子面板迁移），净省 ~450 行。
- 验证：现有 UI 冒烟 + 手工走查「白纸/有数据」两路径各生成一次；PaperEngine 回归测试不动。
- 风险：向导第 7 步已很重（3715 行文件），再吞一个入口加重单文件复杂度；文献搜索流迁移易引入回归。
- 回滚：单提交 revert。

### 方案 B：保留双入口 + 使用埋点
- 边界：两入口零功能改动；新增 `src/ui/usage_probe.py`（约 40 行）：`probe(event, entry)` 追加写 `data/usage_events.jsonl`（本地文件，格式 `{ts, event, entry, extra}`）。埋点点位三处：入口进入（app.py 两个挂载点各一行）、生成触发（paper_writing_ui.py:455 与 undergrad_wizard.py:1378 各一行）、字段完成（可选，A 表单两个 save 按钮 :150/:248）。
- 数据流：Streamlit 事件 → jsonl 追加 → 日间用一行 pandas 脚本汇总月度使用率。
- 规模：~50 行新增，0 删除。
- 验证：跑一次两入口各触发一事件，检查 jsonl 追加；不改任何生成路径。
- 风险：最低；但单人低频使用下埋点积累信号慢（估计需 1-2 个月才有裁决价值），且无法回答「重填成本」这类质性痛点。
- 回滚：删 probe 文件与 5 行调用。

### 方案 C：降级独立入口为「高级模式」（推荐）
- 边界：`app.py:2593-2596` 的挂载从平级菜单改为折叠入口（侧边栏「高级 → 论文工作台（白纸起稿）」+ 一句定位说明「已有分析数据？请走本硕向导」）；`paper_writing_ui.py` 顶部新增可选数据桥——「从向导导入」按钮：若 `st.session_state.undergrad_wizard_data`（app.py:286 已有该会话键）存在第 5 步产物，则一键预填主题/方法两 tab（约 30 行读取+赋值），否则维持现状。
- 规模：~40 行新增、0 删除；不触碰 PaperEngine 与生成路径。
- 验证：手工走查三条路径（无向导数据白纸起稿 / 有向导数据一键预填 / 向导主路径不受影响）；现有测试不动。
- 风险：低——仅 UI 入口层与一次性预填；生成链路零改动。
- 回滚：单提交 revert。
- 附带：可与方案 B 的两行级埋点叠加（入口进入事件），为未来 A/B 决策积累数据。

## 四、推荐与理由（留用户定夺）

**推荐 C（可叠加 B 的入口级埋点）**，理由：
1. 重叠判定是语义级而非代码级——A 的白纸起点与文献搜索是 B 没有的能力，A 全并入（方案 A）会牺牲真实互补面且改动面最大；
2. 用户单人使用、IO/HR 方向论文产出为学期级低频——B 方案埋点要 1-2 个月才有裁决信号，而 C 立即消除「两个平级入口不知道进哪个」的选择成本；
3. C 的「从向导导入」直接消灭信息重填痛点（#L2 的核心抱怨），改动 40 行、零生成链路风险、单提交可回滚。

三方案均为草案，**最终取舍留用户拍板**；拍板后对应实施单可拆夜间执行（C 约 30 分钟级）。
