## 2. 那还剩什么活着？——白名单本身没有判据守着

来账 s923-01 的原话是根因：「新起的 AppTest 文件若不同步追加进这个 set，就**拿不到隔离**，真 AppTest 会往用户真实项目目录里写」。
这条链每修一次（s923-01 → s924-01 → 本单）都只补**一个名字**，而「忘记补名字」这件事从来没有红灯：

1. **漏登记**（新件／改名没进名单）⇒ 静默零隔离，写脏 `~/.psy_analysis` 与项目目录；
2. **死登记**（名单里的名字在盘上不存在）⇒ 覆盖面自欺，看着 10 项、实际护着 7 件；
3. **白名单失去消费方**（fixture 改名／删掉那行 membership 判断）⇒ 前三条一起失效。

本单交付 `tests/test_apptest_whitelist_drift.py` 把这三条各钉一例，另加一例自证（守门件不给自已开后门）。

## 5. 顺带发现的一枚**在册红**（不是本班弄坏的，本班零触碰，交主班／人工处置）

`tests/test_lr_rerun_apptest.py`（s924-59 落下的真 AppTest 件，已登记）在 **HEAD 上单跑即 8 errors，RC=1**：

```
$ .venv/Scripts/python.exe -m pytest tests/test_lr_rerun_apptest.py -q
8 errors in 2.72s        RC=1
  每枚都停在同一处 fixture 自检：
  tests/test_lr_rerun_apptest.py:122  assert not leaked
  AssertionError: src.literature_feed.DB_PATH -> D:\code\psy-analysis\data\literature_feed\feed.sqlite
```

根因定位（只读，三行可复算）：该件 `:39` 在 **collection 期**执行 `from src.literature_feed import paths as feed_paths`，
而 `src/literature_feed/__init__.py:10-18` 用 `from .paths import (… DB_PATH …)` 在**包导入期**复制了一份指向**生产库**的路径常量
（`src/literature_feed/paths.py:17-25` 的 `_resolve_data_root()` 那时还没拿到 `LITERATURE_FEED_DATA_ROOT`）。
fixture 只重指了 `feed_paths.DATA_ROOT/DB_PATH/…` 三个属性，**没重指包命名空间里的那份副本** ⇒
它自己的「扫 `sys.modules` 防泄漏」硬守卫当场判红。8 枚用例一枚没跑到 body，**没有写入生产库**（守卫起作用了）。

两案**待裁决**，本班不动一行：
- A 案（测试侧，小）：fixture 里对 `sys.modules` 扫到的每枚 `src.*` 模块同步重指 `DB_PATH` 等常量；
- B 案（生产侧，行为面）：`src/literature_feed/__init__.py` 不再复制常量（改 `from . import paths` 后按属性访问）。

B 案动的是自学习数据路径面（用户 2026-05-28 明确要求「存储进 D 盘」），按纪律**不属执行班可自裁**。
另注：`conftest.py` 的 AppTest 隔离 fixture 覆盖的是 archive／autosave／project／prefs／usage_logger 五面，
**不含 `literature_feed` 面**——这两枚件并跑时（§4 的 10 枚集合）红相同样只有那 8 项，说明现状没有新增泄漏面，
但「AppTest 是否可能写生产 literature 库」值得单独立一枚治理单。
