## 一、现状摘录（逐字）

- **shim 现实现**（scripts/benchmark_relay_shim.py:87-91）：`record = {"ts": …, "model": …, "status": …, "usage": …}`——**无 err_body**（schema 是 s923-16 的扩展设计稿，未落码）；
- **上游凭据面**：`shim:58` `request.add_header("Authorization", f"Bearer {API_KEY}")`——API_KEY 实发；`shim:6`（load_env_key docstring）「绝不打印/写日志」红线；中转 401/403 时**可能回显请求头片段**进错误体；
- **schema 设计稿已含脱敏**（relay-log-schema 档「截断策略」节，逐字）：①CAP=512 **按字符**截（防 UTF-8 截成非法序列）；②截断前**两条 re.sub 脱敏**（`Bearer <REDACTED>`＋`sk-<REDACTED>`）；③二进制/gzip 替换符 >20% ⇒ 只记 err_kind、err_body=null；④**禁止**整份成功响应体入日志（学生输入回显=隐私面）。

## 二、错误体可能携带的凭据/路径/PII 类别

| 类别 | 来源 | 现设计是否覆盖 |
|---|---|---|
| Bearer token / sk- 系 key | 中转 401/403 回显请求头片段；shim 自发 Bearer | ✅ 两条 re.sub |
| 内网路径/主机名 | 上游异常栈回显（FileNotFoundError 等） | ❌ 未覆盖——错误体自由文本可含 `D:\code\...` 本机路径（本机名/用户名 31563） |
| 学生输入回显（PII 面） | 上游把请求 payload 原样回显的错误形态 | 部分——CAP=512 限制体积；「禁止成功体入日志」只挡 200 面，**错误体回显请求内容未被明确禁止** |
| cookie/session 头 | 极少见于该链路 | ❌ 未覆盖（re.sub 仅两条） |

## 三、三选项对比（日志可见后果）

| 选项 | 行为 | 日志可见后果 |
|---|---|---|
| **维持**（CAP512＋两条脱敏，按设计稿落码） | 错误体前 512 字符可读（凭据已打码） | 根因面可用（「逐题漂移追溯」的设计目的）；路径/PII 类别在 CAP 窗内**仍可能可见**（设计稿未拦） |
| **收紧 CAP**（如 256＋扩充脱敏：路径/用户名 re.sub） | 错误体更短、机读性降 | 根因面受损（512 常一次就够定位）；路径/PII 面补上 |
| **禁记错误体**（err_body 恒 null，只留 err_kind＋err_body_bytes） | 完全无原文 | 隐私最强；根因面归零——「逐题漂移追溯」设计目的落空，err_kind 枚举粒度（5 类）成唯一线索 |

## 四、建议（隐私域不代裁）

设计稿的**四层形态（CAP512＋双脱敏＋二进制闸＋禁成功体）已是三个选项中最平衡的形状**；若主班要再收紧，性价比最高的一步是**补第三条 re.sub（本机绝对路径→`<PATH>`）**——路径/用户名是现设计唯一未覆盖的类别，且与本仓「redact 优先于体积」的既有哲学（s930-14 假绿面、q930-14 同构）一致。**禁记错误体**不建议（目的落空）。本档为备用材料：落码前提＝§1 的排序闸（s927-33：S1 排 #L3 观测面去留之后，若选「停 shim」则本字段全成死码）。
